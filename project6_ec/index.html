Project 6: Extra Credit - FPGA Demo

UW—Madison ECE 552: Fall 2026

Project Introduction

This is an optional extra credit opportunity for Project 6, worth an extra 1% on top of your final course grade. By the end, you will have run a C program on your own pipelined processor on a DE1-SoC board, and measured its CPI on real hardware while changing the memory latency underneath it with the switches.

Your Project 6 submission does not change. Submit it to Gradescope exactly as before.

If you did the Project 3 FPGA demo, this is the same flow with a different processor and a different memory. If you did not, nothing here assumes you did, but there is one comparison you will be asked to make against that build, and the instructions say where to find the numbers.

All material is available in the Project 6 Extra Credit repository on GitHub. Everything except rtl/soc_core.v is finished: the memories, the I/O hardware, the board top level, the displays, the C programs and the whole toolchain are done. Your job is to wire your processor in, verify it in simulation, and compile it in Quartus.

The Demo

To earn the credit, you demo your design in your regular discussion section on 11/18 or 12/2.

IMPORTANT: You will not have access to a board before your demo. This is deliberate: it is how chip design works. A chip team does not get to try its design on silicon and fix it afterwards. It verifies everything it can in simulation and timing analysis, sends the design off to be fabricated, and finds out whether it works when the chip comes back. Here, your simulation and your Quartus timing report are all the evidence you get before the board.

What to Bring

We provide the board and its USB-Blaster cable, and nothing else. We do not provide a computer, so you bring:

  1. Your own laptop with Quartus 25.1 or newer installed, including the Programmer and the USB-Blaster driver (see Requirements). You flash the board from it, so install and check everything before discussion.
  2. A compiled .sof for cpi. A compile takes anywhere from 5-20 minutes, so there is no time to build one in discussion. If you come without one, you will not be able to demo.
  3. Your Quartus project, so you can open the compilation and timing reports from Step 5 during the questions.
  4. Your Project 3 demo's fitter report, if you did that demo. One of the questions is a direct comparison against it. If you did not do it, say so and we will show you ours.
  5. The prediction table from Your Predictions, filled in. We go through it with you at the demo rather than collecting it in advance, so have it on your laptop or on paper.

Note that you do not need a separate .sof for each memory configuration. Both latencies and the initiation interval are set by the switches at reset, not at compile time, so one bitstream covers all of them.

Your Predictions

The demo is an experiment, and you commit to its outcome before you run it.

The instruction memory and the data memory have separate, independently settable latencies. Before you come, work out from your own pipeline diagram what CPI you expect for each workload in each of these four configurations. This table includes the different memory latency configurations you will be asked to demo. Fill in the Predicted column, and write down the reasoning as well as the number.

Config SW[7:0] Workload Predicted CPI Measured CPI
A (1,1 — fastest) 00000000 0 (ALU)
A (1,1 — fastest) 00000000 1 (load/store)
B (1,8 — slow data only) 00111000 0 (ALU)
B (1,8 — slow data only) 00111000 1 (load/store)
C (8,1 — slow instr. only) 00000111 0 (ALU)
C (8,1 — slow instr. only) 00000111 1 (load/store)
D (8,8 — both slow) 00111111 0 (ALU)
D (8,8 — both slow) 00111111 1 (load/store)

That is eight numbers. Bring the table to your demo with Predicted filled in. You fill in Measured at the demo, from the board, and we go through both columns with you; see At the Demo.

IMPORTANT: You are not graded on whether your predictions are correct. You are graded on whether you can explain the result you actually measured. For a prediction that missed badly, you will be expected to explain why your model was wrong.

Before You Come

Since you cannot test on the board, make sure everything you can check passes:

  1. make memtest passes (Step 3). This tests the provided memories, not your processor, so it should pass before you have done anything.
  2. make sim passes, and so does make sweep. The sweep is the important one: it runs your processor at all four configurations above plus the slowest one the switches can select. If it passes at some and fails at others, your processor has a fixed latency baked in somewhere and it will not work on the board.
  3. Quartus compiles with no errors and cpu_clk meets timing (Step 5).
  4. Your prediction table (Your Predictions) has the Predicted column filled in, with your reasoning.
  5. You have read through the flashing steps in Step 6, so you are not seeing them for the first time at the demo.

At the Demo

You power on the board and flash it yourself, in front of us. Then you run the experiment, and write down the results as you go:

  1. Configuration A. Set the switches to that row's SW[7:0] value from your prediction table, press KEY1, read the CPI for workload 0 off HEX3–HEX0. Press KEY0, check LEDR[9] lit to confirm you're now looking at workload 1, and read it again.
  2. Configuration B — data memory eight times slower. Set the switches, press KEY1, read both workloads again.
  3. Configuration C — instruction memory eight times slower instead. Same again.
  4. Configuration D, if there is time.

What We Will Ask About

The questions are about memory, timing and performance: what Quartus reported for your design, what the board measured, and why. You do not need to memorize numbers; have your reports and your prediction table open and find them as we ask.

Memory

  1. Look up what an M10K block is and how its read port works. Your Project 3 build used zero of them and this one uses several. Be ready to explain what changed, and why it is a consequence of the interface your processor presents rather than a decision the tools made.
  2. Both builds have a 4 KB data memory. Explain why one of them costs roughly three quarters of the chip and the other does not.

Timing

  1. Know your cpu_clk Fmax and whether your design meets timing. Be able to say what would happen on the board if it did not.
  2. Be able to explain why your cpu_clk Fmax went up from your Project 3 build.

Performance

  1. Be able to explain CPI differences that are seen in each configuration/workload.
  2. What would you have to change to hide instruction fetch latency?
  3. Which cache would do more for workload 0 — instruction or data? Why?

Your predictions

We will go through your table with you. For each configuration: what did you predict, what did the board say, and if they disagree, what was wrong with your model? Again — being wrong is fine and expected. Not being able to account for it afterwards is not.

The Program: CPI

cpi.c runs a fixed workload, reads the cycle and retired-instruction counters either side of it, and puts the resulting CPI on the displays.

Display Shows
HEX5 instruction memory latency in cycles, 1–8
HEX4 data memory latency in cycles, 1–8
HEX3–HEX0 CPI × 100, in decimal — read 1111 as 11.11
LEDR[3:0] initiation interval, in unary — three lit means 3
LEDR[9] which workload is running (0 = ALU, 1 = load/store)
Control Meaning
KEY0 switch between workloads
KEY1 reset (and re-read the switches)

The switches set the memory timing. They are read only while reset is held, so set them first and then press KEY1:

Switches Sets
SW[2:0] instruction memory latency = SW[2:0] + 1, so 1 to 8 cycles
SW[5:3] data memory latency = SW[5:3] + 1, so 1 to 8 cycles
SW[7:6] initiation interval = SW[7:6] + 1, so 1 to 4 cycles (both)
SW[9:8] not used

A setting written as SW[7:0], like the ones in Your Predictions, runs from SW7 on the left to SW0 on the right, which is the order the switches are in on the board (SW0 is the rightmost). So 00111000 means interval 1 (00), data latency 8 (111) and instruction latency 1 (000): configuration B, labelled (1,8) there, instruction latency first. See Changing the Memory Timing for what latency and interval mean.

The two workloads separate the two things memory latency costs you:

  • Workload 0 is arithmetic only and never touches data memory.
  • Workload 1 walks a small array, so it pays the load cost and then pays again on every load and store.

Step 1: Compiling a Program

From sw/, run:

make PROGRAM=cpi mem

A successful build should output something like:

  ok  cpi            text  xxx  rodata   0  bss  256  stack 3xxx
      ->  build/program.mem (+ 4 byte-lane files for dbus.v)

That one build produces five files, and the hardware loads all of them. build/program.mem is the instruction memory's image. build/program.lane0.mem through build/program.lane3.mem are the same program split into its four byte lanes (lane 0 is bits [7:0] of every word), which is how the data memory loads it — see IP Modules for why it cannot use the single file.

Other commands:

Command What it does
make PROGRAM=yours mem Builds a different program — one you wrote yourself (see Writing Your Own Program). The result always goes to build/program.mem and the four build/program.lane{0-3}.mem files, replacing whatever was there.
make PROGRAM=cpi disasm Prints the RISC-V assembly the compiler generated for that program, with the address and machine-code word of each instruction. Use it to see how your C became instructions, or to find the instruction at a PC while debugging. A copy is also saved to build/cpi.dis whenever you build.
make clean Deletes the build/ directory and everything the build produced. Run it if a build seems stale or you want to start fresh.
make With no arguments, prints this list of commands.

Step 3: Simulating Before You Synthesize

Test the Memories First

From rtl/, run:

make memtest

This checks the provided memories against the Project 6 memory contract, at every latency and interval the switches can select. A passing run ends with:

=== 0 error(s) over 32 configurations ===
all configurations passed

If this fails, the problem is in the provided files rather than your design. Post on Piazza.

make sim    # does it actually run?

A passing run, at the default ILAT=4 DLAT=4 IVL=2, looks like this:

=== soc_tb: cpi   imem latency=4  dmem latency=4  interval=2 ===
  ok   imem latency digit = 00000004
  ok   dmem latency digit = 00000004
  ok   hex_en = 0000003f

Step 5: Compiling in Quartus

Processing → Start Compilation. Expect anywhere from 5-20 minutes.

A successful compile ends with warnings but no errors.

Read the Timing Report

Compilation Report → Timing Analyzer → Slow 1100mV 85C Model → Fmax Summary. This is the fastest your processor could run.

Find the cpu_clk row and compare it against 12.5 MHz, which is what the divider produces. If Fmax is above 12.5 MHz, the design meets timing and you don't need to change anything. If it is below 12.5 MHz (the Setup Summary will also show negative slack for cpu_clk), the processor will not run reliably. Set CLK_DIV_LOG2 = 3 in ip/de1soc_top.v for 6.25 MHz, change -divide_by to 8 and the counter bit to cnt[2] in ip/de1soc.sdc, then recompile.

See What Your Design Became

The fitter report shows what Quartus actually built your design from. Open Compilation Report → Fitter → Resource Section.

Resource Usage Summary gives totals for the whole design. Note these:

Line What it counts
Logic utilization (ALMs needed / total ALMs on device) general-purpose logic cells used
Dedicated logic registers flip-flops
M10K blocks dedicated block RAMs
Total MLAB memory bits logic cells used as small RAMs
Total block memory bits bits held in M10K blocks

Resource Utilization by Entity gives the same counts, broken down by module. Expand the tree to find a row for each part of your design: hart and everything inside it (your rf, alu, …), plus imem, dbus and mmio. Compare the rows against the same table from your Project 3 build. The M10K blocks line and dbus's register count are the two numbers to look at first.

To see it as a picture, Tools → Netlist Viewers → RTL Viewer shows your design as a schematic of the modules you wrote. Technology Map Viewer shows what they became on the FPGA.

Changing the Memory Timing

This needs no recompile. Both latencies and the initiation interval are read from the switches while reset is held:

Switches Sets
SW[2:0] instruction memory latency = SW[2:0] + 1, so 1 to 8 cycles
SW[5:3] data memory latency = SW[5:3] + 1, so 1 to 8 cycles
SW[7:6] initiation interval = SW[7:6] + 1, so 1 to 4 cycles (both)

So the sequence is always: set the switches, press KEY1, read the result.

After reset the switches belong to the running program again, which is why this is sampled at reset rather than wired straight through. The displays show the configuration that was actually sampled.

What the knobs mean:

  • Latency is how long one access takes end to end: assert ren on cycle 0 and valid arrives on cycle latency. The two memories have their own, and that is what the demo is about — see Your Predictions.
  • Interval is how often a new access can start. With interval 2, ready is low on every other cycle. When the latency is longer than the interval, several requests are in flight at once. Both memories share this setting.

Running a Different Program

cd ../sw && make PROGRAM=yours mem
cp build/program.mem build/program.lane0.mem build/program.lane1.mem \
   build/program.lane2.mem build/program.lane3.mem ../rtl/

Then recompile in Quartus.

You have to recompile. The program is not data the board loads at startup; it was baked into the bitstream as the initial contents of the instruction and data memories, so changing a single instruction means re-synthesizing the entire design.

The memory configuration is not like this — both latencies and the interval are runtime settings read from the switches, so one bitstream covers every one of them. Only the program itself needs a recompile.

Each compile overwrites demo.sof. If you build a program of your own as well as cpi, copy each .sof to its own name after compiling it.

Writing Your Own Program

You are encouraged to. Drop a .c file in sw/ and build it:

make PROGRAM=yourprogram mem

The constraint is that your processor implements 37 instructions (the RV32I base set minus a few pieces), so not every legal C program will run on it.

Do not use Why Use instead
*, /, % no multiply or divide instructions shift-and-add; repeated subtraction
long long, float, double no 64-bit or floating-point support 32-bit int / unsigned
printf, malloc, the C library needs ecall, which does not exist here memory-mapped I/O
__builtin_popcount, __builtin_clz, … become library calls write the loop yourself
initialized global variables reset does not reload memory, so they come back stale const globals, or initialize at the top of main

cpi.c is the worked example for most of these: it needs to divide and to multiply by 100 and 10, and does all three with shifts and a subtraction loop.

If you use * or /, the build fails with a clear message rather than producing a program that misbehaves on the board:

ld: undefined reference to `__mulsi3'
ld: undefined reference to `__udivsi3'

That is the linker telling you the compiler wanted a multiply routine your processor does not have.

Note: multiplying by a constant sometimes works and sometimes does not, because the compiler may turn x * 8 into a shift but x * 12500 into a __mulsi3 call.

Byte and half-word access does work (lb, lbu, lh, lhu, sb, sh), so char arrays and strings are fine.

Why no initialized globals: pressing reset restarts your processor but does not reload memory, so a mutable global would come back holding whatever the previous run left in it. crt0 cannot restore it, because there is no separate copy to restore from. Constants go in .rodata, which is never written; mutable state goes in .bss or a local and is set up at runtime. The build enforces this.

If you write a program to measure something, read cpi.c's measure() first. The compiler will happily hoist your workload out from between two counter reads, because the counters are volatile and your workload is not — there is a barrier in there for exactly that reason.

Reference

Memory Map

One flat 4 KB image, loaded into both memories. Each ignores the region it never addresses, which is why one file serves both and crt0 needs no .data copy loop.

Range Contents
0x0000_0000–0x0000_03FF .text, fetched through the imem port
0x0000_0400–0x0000_0EFF .rodata, .bss, reached through the dmem port
0x0000_0F00–0x0000_0FFC stack, grows down

4 KB is not a limit the hardware imposes any more — with the memories in M10K blocks there are 397 of them on this chip, about 4 Mbit in total. It is kept at 4 KB so that the resource numbers are directly comparable against the Project 3 build. IMEM_WORDS and DMEM_WORDS in soc_core.v are what to change if you want more, along with LENGTH in link.ld and MEM_BYTES in sw/Makefile.

Peripherals

Decoded on address bit 31: anything at 0x8000_0000 and above is I/O.

Address Register Dir Meaning
0x8000_0000 LEDR W 10 bits
0x8000_0004 SW R 10 bits, synchronized
0x8000_0008 KEY R 4 bits, active high
0x8000_000C KEY_EDGE R sticky press latch
0x8000_0010 KEY_ACK W write 1 to clear a latch bit
0x8000_0014 HEX_VAL W 24 bits → six hex digits
0x8000_0020 HEX_EN W 6 bits, per-digit blanking
0x8000_0024 CYCLES R free-running cycle counter
0x8000_0028 INSTRET R retired instruction counter
0x8000_002C MEM_CFG R [3:0] imem latency, [7:4] dmem latency, [11:8] interval

The counters are memory-mapped because this ISA has no CSRs; there is no rdcycle to read. They are what cpi.c measures with. Both freeze when the CPU clock stops, so they are still meaningful after a program halts.

MEM_CFG reports the memory timing that was sampled from the switches at the last reset. A program that measures performance can label its own result with it instead of trusting whoever is standing at the board to remember where the switches were. The two latencies are reported separately because they are set separately — see Changing the Memory Timing.

KEY_EDGE is cleared by an explicit write to KEY_ACK rather than by the read itself. Read-to-clear would be safe on a single-cycle processor but would drop presses on a pipelined one that can replay a load.

Peripheral accesses go through the same handshake as memory, with the same latency, so a load from SW takes exactly as long as a load from memory.

IP Modules

The files in ip/ are finished. Do not modify them.

File Role
de1soc_top.v Board top level: pins, reset, clock, LED override, displays
mem_pipe.v The handshake: ready/interval, the configured latency, in-order responses
imem.v 4 KB instruction memory, request/response, block RAM
dbus.v 4 KB data memory plus the peripheral split, request/response, block RAM. Storage is four separate byte-lane arrays rather than one word-wide array, each loaded from its own program.lane{0-3}.mem -- a single word-wide array with byte-enable writes does not synthesize into M10K blocks on this toolchain.
mmio.v Switches, buttons, LEDs, displays, counters
hex7seg.v Hex digit → seven segments
clkdiv.v 50 MHz → 12.5 MHz CPU clock, freezes on halt
halt_ctrl.v Watches your retire interface for ebreak and traps
soc_tb.v The SoC testbench. Simulation only; never add to Quartus
mem_tb.v The memory self-test. Simulation only; never add to Quartus
de1soc.sdc Timing constraints; add to Quartus

mem_pipe.v is worth reading even though you do not have to touch it. It is about eighty lines, and it is the whole mechanism behind a multi-cycle memory: a shift register of in-flight requests, a counter for the initiation interval, and a tap that picks which stage the storage actually gets accessed from. The storage behind it only ever sees a plain one-cycle synchronous access, which is what makes it a block RAM.

Board Behavior

  1. Reset is KEY1. It also re-samples the memory configuration from SW[7:0].
  2. All LEDs on, steady: your program executed ebreak and the CPU stopped. Normal for a program that ends.
  3. All LEDs blinking: your processor took a trap (illegal instruction, misaligned load/store, or misaligned branch target). These programs do none of those, so blinking points at the processor, not the software.
